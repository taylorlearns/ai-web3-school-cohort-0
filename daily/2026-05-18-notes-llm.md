## 一、LLM 是什么

LLM（Large Language Model）不是一个会聊天的黑盒，而是把大量文本、代码和多模态信号压进参数里的**概率模型**。

> 核心认知：**LLM 生成的是概率上合理的输出，而不是天然可信的事实。**

这决定了 LLM 在任何严肃系统里的位置——它可以帮你理解、归纳、生成和规划，但不能单独承担事实来源、权限判断和最终执行。

---

## 二、5 个关键概念

### 1. Token 🧩
模型处理文本的最小单位，不是"字数"，而是 tokenizer 切分后的片段。
- 直接影响：上下文容量、调用成本、信息完整性
- 注意：代码、JSON、长标识符比普通段落更吃 token

### 2. Embedding 🧲
把文本转成向量，用来衡量"语义接近度"。
- 适合：搜索、聚类、推荐、RAG
- 不适合：判断结论是否正确（向量相似度 ≠ 事实正确性）

### 3. Transformer 🏗️
核心架构，靠 attention 机制在上下文里找模式。
> Transformer 给了模型强大的模式组合能力，但没有给它事实最终裁决权。

### 4. Hallucination 👻
模型编造合理但错误的内容。
- 在普通问答里：质量问题
- 在带执行能力的系统里：**流程风险**
- 处理方式要"两头堵"：

| 前治理（源头） | 后治理（结果） |
|:-------------|:-------------|
| 写好 prompt | 外部校验（schema/规则） |
| RAG 注入高质量上下文 | 人工审核 |
| 限定回答边界 | 审计日志 |

> 纯靠后治理像"抽卡"，效率不高；前后结合才是生产级方案。

### 5. Multimodal 🎨
处理文本+图片+音频的多模态模型。
- 价值：让模型读懂截图、图表、控制台、设计稿
- 边界：关键判断仍要回到结构化数据和可信来源

---

## 三、在 AI × Web3 中的位置

```
用户目标 → [LLM: 理解与生成层] 
         → 数据层（RPC/索引器/预言机）
         → 编排层（Prompt/Context/RAG/Agent）
         → 执行层（工具调用/钱包/合约）
         → 安全层（校验/权限/日志）
```

**越靠近执行层，越要把 LLM 的自然语言输出变成可验证对象。**

---

## 四、最小实践思路

"交易解释器"：输入一笔交易哈希 → 链上读数据 → LLM 解释
练习重点：把 **模型生成、链上事实、来源边界、不确定性** 分开。

---

## 五、我的思考

**防幻觉的"前治理 vs 后治理"策略：**
- Handbook 说"不要只靠写更好的 prompt"
- 但实际工程里，prompt + RAG 这套前治理能挡掉 80-90% 的问题
- 最合理的方案是**两头堵**：源头优化 + 结果校验

从 DevRel 角度迁移：
- 写教程时 → 前治理（prompt 清晰 + 引用准确）+ 后治理（跑一遍验证再发）
- 做社区内容 → 前治理（定好回答边界）+ 后治理（敏感内容过滤）
